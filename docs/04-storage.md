# 04 · 数据存储方案与取舍

> 状态：✅ 全部已定（2026-08-03）：**不建数据库，直接存多维表格类工具**；工具已定为**飞书多维表格**（samuel 问答确认），提醒通道为飞书群机器人。

## 决策记录（2026-08-03）

samuel 与合作方对话定稿，核心推理：

> 如果存数据库，就还需要做数据展示，一定会需要一定的后端；如果不存数据库（直接存多维表格类工具），那么后端 + 数据展示就都不需要了。前期多维表格完全满足需求；未来采集团队壮大后，再转成后台数据存储方案——到那个时间点做一次迁移就好，不麻烦。

**结论：主存储 = 多维表格类 SaaS，无数据库、无后端、无自建数据展示。**

## 本质问题

存储选型的真实问题不是"用什么数据库"，而是**"谁用什么界面看这些报名数据"**。多维表格类工具的价值：存储和展示是同一个东西——运营直接在里面浏览、筛选、建视图、配自动化，零开发。

## 工具候选（四选一，按团队实际使用的协作生态定）

| 选项 | API | 免费额度 | 备注 |
|---|---|---|---|

## 写入链路与失败处理

```
函数验证通过
  → 写入多维表格（这一步就是"落库"，失败则整个请求报错）
  → 发邮件（DirectMail）+ IM 群机器人提醒
```

因为没有兜底数据库，**写入多维表格失败必须让用户可感知**：前端提示"提交失败请重试"并展示备用联系邮箱；同时触发告警（IM 机器人）。SaaS 短暂故障靠用户重试覆盖，可接受（低频表单场景）。

*可选增强（当前决策为不做，仅记录）*：若日后对"单一 SaaS 故障丢线索"在意，可在函数里加约 20 行先写 Cloudflare D1 再同步多维表格——D1 只做静默备份、不做展示，不改变"无后端无展示"的性质。列在这里备查，不影响当前架构。

## 未来迁移路径（采集团队壮大 → 自建后端 + 数据库）

1. 新后端建库（届时按业务实际字段设计）；
2. 多维表格全量导出（CSV 或 API 拉取）一次性导入；
3. 官网函数只改一处"写入目标"（多维表格 API → 新后端 API），前端零改动；
4. 多维表格可保留作运营视图（新后端反向同步）或退役。

一次性工作量约半天到一天，验证了"现在不为未来预付成本"的决策正确。
